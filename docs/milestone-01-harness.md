# 1차 마일스톤 — 데스크톱 하네스 기반 설계

상태: **기획·설계 초안. 구현 및 실제 연결 검증은 아직 진행하지 않음.**

이 세션은 기획을 담당한다. 사용자가 제시한 마일스톤을 기능 범위·화면·동작 흐름·확인 기준으로 구체화하며, 애플리케이션 구현은 별도 지시에 따른다.

## 목표와 범위

사용자가 제시한 목표는 **데스크톱 UI 기반 하네스 설계**이며, 핵심은 **Codex OAuth 연결, 모델 호출 및 답변 확인, 도구 사용**이다.

이번 설계는 단일 대화에서 이 흐름을 연결하는 기반에 집중하는 안으로 정리한다. 멀티 에이전트 협업과 Obsidian 메모리 연동은 전체 MVP 범위로 유지하되, 이번 마일스톤의 구체화 대상과 분리한다. 이후 마일스톤은 사용자가 제시한다.

## 기능별 설계 항목

| 영역 | 설계할 내용 | 구현 후 확인할 동작 |
|------|-------------|--------------------|
| 데스크톱 UI | 연결 상태, 모델 선택, 입력·답변, 도구 요청·결과, 실행 상태 | 한 화면에서 요청부터 결과까지 확인 가능 |
| Codex OAuth 연결 | 로그인 시작·결과, 현재 연결 상태, 로그아웃, 인증 오류·만료 대응 | 로그인 성공과 실패가 구분되고 해제 후 연결 상태가 갱신됨 |
| 모델 호출 | 모델 목록·선택, 사용자 입력 전달, 응답 수신과 대화 유지 | 선택한 모델로 요청을 보내고 후속 질문을 이어감 |
| 답변 확인 | 스트리밍·최종 답변, 응답 완료·실패·사용자 중단 표시 | 일부 답변이 보이는 것과 정상 완료를 구분함 |
| 도구 사용 | 사용할 도구와 범위, 실행 전 확인, 실행·결과 반환, 오류 처리 | 모델의 도구 요청이 실제 실행 결과로 이어지고 답변에 반영됨 |
| 실행 제어 | 실행·확인 대기·중단·실패 상태와 재시도 표시 | 사용자가 진행 상태를 알고 제어할 수 있음 |

여기서 답변 확인은 **호출 결과가 정상 수신·표시되었는지 확인하는 것**이다. 답변 내용의 정답 여부를 자동 판정하는 별도 검증 시스템은 이번 목표로 추가하지 않는다.

## 구조 초안

```text
데스크톱 UI
    ↕ 요청·상태·답변·도구 실행 확인
Artemis 하네스
    ↕ 인증·대화·모델·도구 이벤트
Codex 연동부
    ↕
Codex 런타임 / 모델 서비스 / 허용된 로컬 도구
```

- **UI:** 사용자 입력과 판단을 받고 현재 상태·결과를 표시한다.
- **하네스:** 요청과 실행 상태를 관리하고 사용자 지시 범위 및 도구 허용 범위를 적용한다.
- **Codex 연동부:** 로그인, 모델 호출, 응답·도구 이벤트를 하네스에 연결한다.

로컬 기반은 데스크톱 앱과 하네스의 실행 위치를 뜻한다. OAuth 인증과 원격 모델 호출을 오프라인 기능으로 가정하지 않는다.

## 최소 화면 구성안

| 영역 | 표시·조작 내용 |
|------|----------------|
| 연결·모델 | 로그인/로그아웃, 연결 상태, 선택 모델 |
| 대화 | 입력, 전송, 진행 중 답변과 최종 답변 |
| 도구 | 도구명·입력·대상 확인, 실행 판단, 결과·오류 |
| 실행 상태 | 대기·실행·사용자 확인 대기·완료·실패·중단, 중단 요청과 재시도 횟수 |

실제 화면 배치와 데스크톱 프레임워크는 미정이다. 전체 제품의 프로젝트 관리·메모리 탐색 등 화면은 이 최소 화면 설계와 구분한다.

## 기본 동작 흐름

1. 사용자가 GUI에서 Codex 로그인을 시작하고 인증 결과를 확인한다.
2. 사용할 모델을 선택하고 요청을 전송한다.
3. 하네스는 답변을 수신하고 GUI에 진행 상태와 함께 표시한다.
4. 도구가 필요하면 도구명·입력·대상을 보여주고 사용자 판단을 받는다.
5. 허용된 도구를 실행하고 결과를 모델에 돌려줘 최종 답변으로 연결한다.
6. 실행 완료·실패·사용자 중단을 구분해 표시한다.

도구 실행 전 확인은 **초기 설계 제안**이며, 승인 단위와 재사용 범위는 별도 결정한다. 프롬프트 지시만으로 범위 제한이 보장된다고 간주하지 않는다. 선택한 연동 방식에서 내장 도구를 포함한 실제 실행 경로에 제한을 적용할 수 있는지 확인해야 한다.

기본 원칙은 사용자 지시 범위를 넘는 행동을 하지 않는 것이다. 재시도는 최대 5회이며 작업 시간·사용량 제한은 두지 않는다. 결과가 불명확한 도구 실행을 자동 반복하지 않도록 설계한다. 재시도 적용 단위와 자동·수동 여부는 미정이다.

## 연동 후보와 공식 문서 확인

**Codex app-server를 우선 검토할 후보로 제안한다.** 공식 문서는 로컬 프로세스와 연결해 인증, 대화, 스트리밍, 도구 상태, 승인 요청과 중단을 처리하는 인터페이스를 제공한다. 관리형 ChatGPT 로그인은 `account/login/start`의 `chatgpt` 방식으로 브라우저 인증을 시작한다. [공식 app-server 문서](https://learn.chatgpt.com/docs/app-server)

앞서 조사한 Sign in with ChatGPT 토큰을 앱이 직접 관리해 app-server에 공급하는 경로도 별도로 있다. 두 경로를 혼용하지 않고, 구현 설계 시 인증 수명주기를 누가 관리할지 정한다. 모델 목록 표시만으로 사용 권한을 확인했다고 보지 않으며 실제 요청의 정상 완료로 검증한다. [공식 OAuth 토큰 연동 문서](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server)

토큰 직접 공급 경로에는 도구 지원 제약이 있다. 로컬 도구와 호스팅 도구를 구분하고, 초기 도구가 해당 경로에서 동작하는지 확인한다. [공식 프리뷰 제약](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations)

위 내용은 2026-10-28 공식 문서 조사 결과이며 Artemis의 연결 성공을 의미하지 않는다. 현재 코드·계정 인증·모델 추론·도구 실행 테스트는 수행하지 않았다.

## 설계 산출물과 향후 확인 기준

이 기획 세션의 산출물은 **기능 범위, 화면 구성안, 구성 요소별 책임, 정상·오류 흐름, 구현 후 확인 시나리오**다. 아래는 전체 제품의 완료·중단 정책 확정이 아니라, 이번 기능을 구현했을 때 사용할 확인 기준의 초안이다.

| 시나리오 | 확인 기준 |
|----------|-----------|
| OAuth 로그인·취소·실패·해제 | 상태가 구분되고 실패 원인이나 다음 행동을 확인 가능 |
| 일반 요청과 후속 질문 | 선택 모델의 답변이 표시되고 대화 맥락이 이어짐 |
| 정상 응답·통신 실패·중단 | 일부 출력이 있어도 실패·중단을 정상 완료로 표시하지 않음 |
| 대표 도구 실행 | 요청 → 사용자 확인 → 실제 실행 → 결과 반환 → 답변 흐름 확인 |
| 도구 거부·범위 밖 요청·실행 실패 | 거부한 동작과 허용 범위 밖 동작은 실행되지 않으며 오류를 확인 가능 |
| 재시도·사용자 중단 | 정한 적용 단위에서 재시도 5회 한도를 지키고, 중단 요청 뒤 새로운 실행을 시작하지 않음 |

첫 대표 도구는 프로젝트 내 파일 조회 또는 지정 명령 실행 등을 후보로 두며, 종류와 허용 범위는 아직 확정하지 않는다. 도구를 사용했다는 답변만으로 성공 처리하지 않고 실행 기록과 실제 결과를 확인한다.

## 후속 결정 사항

- 데스크톱 구현 기술과 Codex app-server 채택 여부, 인증 관리 방식.
- 기본 모델과 선택 가능한 모델의 표시 방식.
- 최초 지원 도구, 작업 대상 범위, 사용자 확인 단위.
- 재시도 카운트의 적용 단위와 재시도 방식, 진행 중 도구의 중단 처리.

결정되지 않은 항목은 후속 기획에서 정하며, 이 문서를 애플리케이션 구현 승인으로 사용하지 않는다.
